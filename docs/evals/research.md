# Research notes: workflow evaluations for Mike

Research checked 2026-10-26. This memo translates primary research into a proposed Mike design; it does not establish Mike's current model quality or production readiness. No live model evaluations were run.

## Proposed eval-generation process

These are Mike design recommendations, not numerical standards established by the papers.

1. **Start with actual task contracts.** For each major product workflow, document user intent, fixture state, tool permissions, what a successful outcome looks like, fatal violations, and a reference solution. Turn audit defects and existing manual checks into regression cases. Mark newly generated cases as drafts until reviewed.
2. **Build scenario families before paraphrases.** Use a source matter to create ordinary, absent-information, conflicting-evidence, long-context, malformed-input, and adversarial variants. Add “should act” and “should abstain/clarify” counterparts. Vary material facts, evidence position, clauses, and permissions; paraphrasing alone does not create independent coverage.
3. **Ground every expectation.** Issue labels, dates, amounts, parties, permitted changes, and acceptable answers need a source span or explicit product policy. Include alternative valid outputs and partial-credit criteria where appropriate. Legal expert review is required before calling synthetic legal labels gold.
4. **Control provenance and access.** Record origin/license or consent basis, jurisdiction and effective date, source hashes, parent scenario family, reviewer and adjudication state. Separate development, judge-calibration, and release holdout matter families before generating variants. Public CI fixtures must be wholly synthetic or appropriately licensed; actual client material belongs in an access-controlled corpus.
5. **Test the graders themselves.** A reference output must pass. Mutations such as a changed amount, omitted material issue, fabricated pinpoint citation, unauthorized scope, missing edit, or corrupted export must fail the intended checks. Build injection attempts into candidate outputs to ensure the judge treats them as data. Candidate observations must not supply their own authoritative pass/fail labels.
6. **Adjudicate and version.** Preserve disagreements and insufficient-evidence verdicts. Require independent review for ambiguous/high-impact labels, revise unclear tasks, and version case sets and rubric changes. Cases generated by a model and judged by that same model are proposals, not independently validated truth.

## Proposed agent architecture

Use explicit artifacts and bounded responsibilities rather than letting one agent invent, execute, and certify its own work:

- **Curator:** proposes cases from sanitized failures and workflow contracts; produces candidate cases and provenance.
- **Reviewer:** checks solvability, evidence, split-family separation, ambiguity, and permitted actions; promotes cases through draft → reviewed → adjudicated.
- **Runner/controller:** freezes case/model/prompt/tool/catalog versions, creates clean trial state, enforces deadlines and budgets, schedules repeats, and records observations. It is deterministic orchestration, not an LLM making release decisions.
- **Grading workers:** deterministic checks inspect artifacts/state; calibrated model judges assess genuinely semantic legal criteria. Judges cannot invoke candidate tools or modify product state. They return criterion verdicts, short evidence-backed explanations, and “insufficient evidence.”
- **Adjudicator:** routes disagreement, novel failures, and calibration misses to human reviewers. An automatic model consensus cannot establish legal ground truth.
- **Reporter:** aggregates frozen results and uncertainty, including coverage gaps, errors, latency, cost, and model/config provenance. Policy decides eligibility before ranking eligible candidates.

These roles can initially be functions/processes with typed JSON inputs; adding autonomous LLM agents is not necessary for every role.

## Proposed model and performance comparison protocol

Freeze the same source fixtures, workflow version, tools, permissions, output constraints, and sampling budget for each comparison. Store the resolved model snapshot, provider, parameters, reasoning configuration, prompt hash, source/code/catalog commit, and tool environment. Compare a model-only ablation separately from a tuned-system comparison so prompt or retrieval changes are not mislabeled model improvements.

Pair models on identical cases and scheduled repeat indices. Use matter/scenario families as statistical clusters when generating confidence intervals; repeated trials or paraphrases are not independent matters. Report denominators, ties, invalid/insufficient observations, tool/environment failures, and all scheduled attempts. Set any minimum sample sizes, non-inferiority margins, latency budgets, and promotion thresholds with product/legal owners before looking at candidate results; label them provisional until calibrated.

For each workflow and important risk slice, report task success, material error/omission rate, fatal violations, and grade coverage. For extraction add field-level precision/recall; for review add issue precision/recall; for RAG separate retrieval evidence recall, claim support, and citation coverage. Diagnostic scores can award partial credit while critical violations still fail task eligibility.

Measure queue delay, time to first useful visible output, time to final usable persisted artifact, per-stage durations, token/tool usage, timeout/retry rate, and billed cost. Keep judge cost separate from candidate cost. Count failed attempts in total spend and cost per successful task; missing prices are unknown rather than zero. Report p50/p95 with sample counts, concurrency, cache state, document sizes, and environment. Run controlled load tests separately from quality trials so contention is not mistaken for model latency. These proposed measurements require real observations; replayed fixture results validate the harness, not Mike or any model.
